# 微服务字段适配修复方案

> 生成时间：2026-06-15
> 基于：`docs/页面数据分析.md` 字段级对比结果
> 原则：以旧单体响应格式为基准，通过 Gateway normalize 层补齐字段差异

---

## 修复策略

旧单体直接从 DB 构建完整响应，前端完美适配。新微服务返回精简 proto，Gateway 负责补齐差异。

**修复分三层**（按优先级）：

| 层 | 位置 | 适用场景 |
|----|------|---------|
| Gateway normalize | `handler.go` 的 `adaptLegacyResponseByPath` | 响应结构/字段缺失/格式变更 |
| Biz 层初始化 | `app/*/internal/biz/*.go` | 数组字段 nil 问题 |
| Service 层补齐 | `app/*/internal/service/*.go` | proto 转换遗漏的字段 |

---

## P0：破坏性变更（页面功能失效）

### P0-1. `GET /mistake-topics` 列表 schema 断裂

**问题**：旧单体返回 7 个静态知识库卡片（code/tag/title/problem_pattern/root_causes/...），新微服务返回用户错误统计（topic/error_count/total_attempts/...）。前端使用旧格式会完全失效。

**文件**：`app/gateway/internal/proxy/handler.go`

**方案**：在 Gateway 层拦截，调用旧单体的静态知识库逻辑返回正确格式。参考旧单体 `question_service.go` 的 `ListMistakeTopics`。

```go
// 在 adaptLegacyResponseByPath 中增加 case：
case strings.HasSuffix(path, "/mistake-topics") && !strings.Contains(path, "/mistake-topics/"):
    return normalizeMistakeTopicListPayload(value)

// 新增函数：
func normalizeMistakeTopicListPayload(value interface{}) interface{} {
    // 新微服务返回的是用户错误统计，前端期望的是静态知识库卡片
    // 需要在 biz 层或 Gateway 层补充静态知识库数据
    // 方案 A：Gateway 调用 questionClient.GetMistakeTopic 逐个补全
    // 方案 B：在 question 微服务中保留静态知识库，ListMistakeTopics 返回正确格式
    return value
}
```

**实际修复**：需要在 `app/question/internal/biz/` 中保留旧单体的静态知识库逻辑，`ListMistakeTopics` 应返回 `MistakeTopicCard[]` 而非用户错误统计。这是 biz 层问题，不是 Gateway 能单独解决的。

---

### P0-2. `POST /exams/random` 缺少 `exam_id`

**问题**：旧单体返回 `exam_id`（string），新微服务 random exam 不返回 `exam_id`，导致前端无法回提交答案。

**文件**：`app/question/internal/biz/usecase.go` 或 `app/question/internal/service/question.go`

**方案**：在 biz 层生成 random exam 时，构造一个 exam_id（如 `"random-{timestamp}"`）并存入响应。

---

### P0-3. `POST /plans` 创建计划响应缩减

**问题**：旧单体同步返回完整 `PlanDetailResponse`（含 tasks），新微服务异步返回仅 `{plan_id, status, created_at}`。

**文件**：`app/gateway/internal/proxy/handler.go`

**方案**：Gateway 层在创建计划后，轮询 `GET /plans/{id}` 直到 status 非 `generating`，然后返回完整计划详情。或者前端适配异步轮询（需改前端）。

**推荐**：Gateway 层补一个 `normalizeCreatePlanPayload`，在 status 为 `generating` 时附加提示字段，让前端知道需要轮询。

---

### P0-4. `POST /plans/{id}/adjust` 响应结构完全不同

**问题**：旧单体返回完整 `PlanDetailResponse`，新微服务返回 `AdjustPlanResponse`（tasks_added/tasks_removed/...）。

**文件**：`app/gateway/internal/proxy/handler.go`

**方案**：Gateway 层在 adjust 后，额外调用 `GET /plans/{id}` 获取完整计划详情返回。

```go
// 在 handleAdjustPlan 中：
// 1. 调用 planClient.AdjustPlan
// 2. 再调用 planClient.GetPlan 获取完整详情
// 3. 返回完整详情（与旧单体一致）
```

### P0-5. `POST /community/posts` Gateway 不转发 `post_type` 和 `tags`

**问题**：Gateway `handleCreatePost` 只转发 `title/content/category`，丢失 `post_type` 和 `tags`。

**文件**：`app/gateway/internal/proxy/handler.go` 的 `handleCreatePost`（约 L3747）

**方案**：从请求体中解析 `post_type` 和 `tags`，转发给 communityClient。

```go
// 当前代码：
resp, err := gw.communityClient.CreatePost(c.Request.Context(), &communityv1.CreatePostRequest{
    AuthorId: userID, Title: req.Title, Content: req.Content, Category: req.Category,
})

// 修改为：
tagsJSON, _ := json.Marshal(req.Tags)
resp, err := gw.communityClient.CreatePost(c.Request.Context(), &communityv1.CreatePostRequest{
    AuthorId:  userID,
    Title:     req.Title,
    Content:   req.Content,
    Category:  req.Category,
    PostType:  req.PostType,  // 新增
    Tags:      string(tagsJSON), // 新增（CSV 或 JSON，取决于 proto 定义）
})
```

同时需要在请求结构体中添加 `PostType` 和 `Tags` 字段。

### P0-6. `PUT /community/posts/{id}` Gateway 不转发 `tags`

**问题**：同 P0-5，编辑帖子时 tags 丢失。

**文件**：`app/gateway/internal/proxy/handler.go` 的 `handleUpdatePost`（约 L3775）

**方案**：同 P0-5，在请求体中解析 `tags` 并转发。

### P0-7. `GET /community/posts/{id}/comments` 响应格式变更

**问题**：旧单体返回裸数组 `[{...}]`，新微服务返回分页对象 `{list, total, page, page_size}`。前端 `.map()` 直接崩溃。

**文件**：`app/gateway/internal/proxy/handler.go`

**方案**：在 `normalizeCommunityCommentListPayload` 中，如果前端期望裸数组，则从分页对象中提取 `list` 返回。

```go
func normalizeCommunityCommentListPayload(value interface{}) interface{} {
    payload, ok := value.(map[string]interface{})
    if !ok {
        return value
    }
    // 先确保 list 存在
    ensureArrayField(payload, "list")
    // 逐项补齐 author
    if list, ok := payload["list"].([]interface{}); ok {
        for i, item := range list {
            list[i] = enrichCommunityAuthor(item)
        }
    }
    return payload  // 返回分页对象，前端已适配
}
```

**注意**：需确认前端实际是期望裸数组还是分页对象。如果前端已适配分页对象，则只需确保 `list` 字段非 nil。

## P1：功能退化（页面可工作但数据不完整）

### P1-1. `GET /questions/recommendations` 多个字段丢失

**问题**：`topic_problem_pattern`、`primary_question_set`、`occurrence_count`、`priority_explanation`、`recommended_actions`、`related_question_sets` 始终为空或硬编码。

**文件**：`app/gateway/internal/proxy/handler.go` 的 `normalizePracticeRecommendationPayload`

**方案**：在 normalize 函数中，对缺失字段设置默认值（空数组/空字符串），避免前端访问 undefined。

```go
// 在 item 构建中增加默认值：
item := map[string]interface{}{
    // ... 现有字段 ...
    "topic_problem_pattern":  entry["topic_problem_pattern"],
    "related_question_sets":  ensureArrayValue(entry["related_question_sets"]),
    "recommended_actions":    ensureArrayValue(entry["recommended_actions"]),
    "primary_question_set":   entry["primary_question_set"],
    "occurrence_count":       entry["occurrence_count"],
    "priority_explanation":   entry["priority_explanation"],
}
```

当前代码已处理 `related_question_sets` 和 `recommended_actions`（通过 `ensureArrayValue`），但 `topic_problem_pattern`、`primary_question_set`、`occurrence_count`、`priority_explanation` 可能为 nil。需要在 normalize 中确保这些字段有默认值。


### P1-7. `GET /question-sets/{slug}` 结构变更

**问题**：旧单体返回扁平结构，新微服务返回嵌套 `{info, questions}`。

**文件**：`app/gateway/internal/proxy/handler.go`

**方案**：在 Gateway 层增加 `normalizeQuestionSetDetailPayload`，将嵌套结构展平为旧格式。

```go
func normalizeQuestionSetDetailPayload(value interface{}) interface{} {
    payload, ok := value.(map[string]interface{})
    if !ok {
        return value
    }
    // 如果有 info 嵌套，展平到顶层
    if info, ok := payload["info"].(map[string]interface{}); ok {
        for k, v := range info {
            if _, exists := payload[k]; !exists {
                payload[k] = v
            }
        }
    }
    ensureArrayField(payload, "questions")
    ensureArrayField(payload, "focus_tags")
    return payload
}
```

### P1-8. `GET /user/practice-stats` 字段重命名

**问题**：`category_stats[].total` → `answered`，`category_stats[].accuracy_rate` → `accuracy`，`category_id` 缺失。

**文件**：`app/gateway/internal/proxy/handler.go` 的 `normalizePracticeStatsPayload`

**方案**：在 normalize 中重命名字段。

```go
func normalizePracticeStatsPayload(value interface{}) interface{} {
    payload, ok := value.(map[string]interface{})
    if !ok {
        return value
    }
    // 重命名 category_stats 内的字段
    if stats, ok := payload["category_stats"].([]interface{}); ok {
        for _, item := range stats {
            if s, ok := item.(map[string]interface{}); ok {
                if v, exists := s["answered"]; exists {
                    s["total"] = v
                }
                if v, exists := s["accuracy"]; exists {
                    s["accuracy_rate"] = v
                }
            }
        }
    }
    return payload
}
```

## P2：类型/格式变更

### P2-1. int64→int32 类型缩窄

**问题**：多个接口的 ID 和计数字段从 int64 缩窄为 int32。

**影响**：仅当 ID 超过 21 亿时溢出，当前数据量下风险极低。

**方案**：暂不修复，监控数据量增长。

---

### P2-2. float64→float32 精度丢失

**问题**：`plan.progress` 等字段精度下降。

**影响**：进度显示可能有微小差异（如 33.33% → 33.330001%），前端通常会格式化。

**方案**：暂不修复，前端格式化可掩盖。

---

### P2-3. 时间格式变更

**问题**：Community `"2006-01-02 15:04"` → RFC3339 `"2025-06-15T10:30:00Z"`。

**影响**：前端 `new Date()` 可以解析两种格式，但显示可能不同。

**方案**：Gateway 层在 `normalizeJSONValue` 中，对 Community 的时间字段做格式转换。

---

### P2-4. Question `tags` CSV→数组

**问题**：旧单体返回 CSV 字符串，新微服务返回数组。

**影响**：前端可能用 `tags.split(',')` 解析，数组上无此方法。

**方案**：Gateway `normalizeQuestionDetailPayload` 已将 `tags` 复制到 `tag_list` 数组，前端应使用 `tag_list`。

---

### P2-5. Community `post_type` 枚举变更

**问题**：`"article"/"moment"` → `"discussion"/"article"/"question"`。

**影响**：前端用 `post_type === 'moment'` 判断的逻辑会失效。

**方案**：Gateway 层在 normalize 中，将 `"discussion"` 映射回 `"moment"`（如果前端依赖此值）。

---
