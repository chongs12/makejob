# MakeJob 开发准则 3

> **文档目的**
>
> 本文是 `docs/开发准则.md`、`docs/开发准则2.md` 的第三份补充，专门针对 **前后端 API 契约对齐、Proto 响应 message 设计、Gateway 响应整形（BFF reshape）、字段命名与结构映射** 这一类问题。
>
> 这些规则来自本轮对六个服务（Interview / Question / Plan(Companion) / Community / Admin / Growth）响应结构的复审修复经验。
>
> 准则2 关注的是“微服务边界、能力归属、MQ 状态机、鉴权透传”这类**服务间链路**问题；本文关注的是更靠前端的一层：**gRPC 服务返回的数据结构，和前端实际消费的数据结构，根本对不上**。这两类问题正交，都会造成“后端自测通过、前端一跑就报错或白屏”。

---

## 一、这轮问题为什么会出现

### 1. 核心病根：Proto 响应 message 被当成“后端内部结构”来设计，而不是“前后端契约”

本轮几乎所有问题都是同一个模式：

- 后端定义 `XxxResponse` / `XxxDetail` 时，只写了“后端当前手头有的字段”。
- 前端的 TypeScript interface 却按照“页面渲染真正需要的字段”来声明。
- 两者从来没有被放在一起逐字段比对过。

结果就是 proto 里有 8 个字段，前端 interface 里有 20 个字段，中间 12 个字段缺失或结构不同。后端编译通过、单测通过，因为后端测试根本不知道前端要那 12 个字段。

**Proto 的 response message 不是后端的私有 DTO，它是对外契约。** 设计它时的唯一权威依据，应该是**前端的消费代码**，而不是“后端 biz 层现在能拿到什么”。

### 2. “扁平 vs 嵌套”的结构错配，比“缺字段”更隐蔽

缺字段至少会是 `undefined`，前端如果有可选链还能扛住。但**结构形态错配**会直接让整页逻辑失效：

- 后端返回扁平的 `InterviewReport`，前端却读 `reportQuery.data.report.xxx`（多套了一层 `report` 包装）。
- 后端返回 `{questions, reason}`，前端却要 `{focus_tags, items:[{question:{...}, focus_tag,...}]}`（列表项需要被重新包成带元数据的对象）。
- 后端返回扁平的 `author_id` / `author_name`，前端却要嵌套的 `author:{id, username, avatar}`。
- 后端单字段消息 `{configs:[...]}` 被网关通用解包逻辑折叠成**裸数组**，前端却要 `{configs, providers, default_bindings}` 三字段对象。

这类问题的特征是：**字段“都在”，但放的层级/容器不对**。前端 `data.report` 是 `undefined`、`data.items` 是 `undefined`、`data.configs` 是 `undefined`，整块功能直接消失，且不一定报错——很多时候是静默白屏。

### 3. CSV 字符串 vs 数组：同一份数据的“序列化形态”不一致

后端域模型里 `Tags` 是 `"go,mysql,redis"` 这样的 CSV 字符串（数据库存储形态），前端 interface 里 `tags` 是 `string[]`，并且直接 `post.tags.map(...)` 渲染标签。

后端如果把 CSV 字符串原样塞进 proto 的 `string tags` 字段透传出去，前端 `.map` 就会在字符串上调用，行为完全错误（字符串没有 `.map`，会直接抛 `TypeError`）。

**数据的存储形态、传输形态、消费形态可以不同，但必须在某一层显式转换，并且约定清楚是哪一层。**

### 4. “后端能编译” ≠ “契约正确”，因为缺了前端这一侧的验证

本轮所有后端改动都能 `go build` + `go test` 通过。问题恰恰是：Go 的测试只能验证“后端自己说的话自洽”，验证不了“前端听到的话是不是它要的”。

真正能发现这类问题的验证手段是：
- 把 proto/网关输出的 JSON，和前端 TS interface 逐字段比对；
- 或前端 `tsc --noEmit` / 真实页面跑一遍。

而这些在“只改后端”的工作流里很容易被跳过。

### 5. 生成代码的 `omitempty` 让“缺失”变成“静默缺失”

protobuf 生成的 Go 结构体，JSON tag 默认带 `omitempty`。这意味着：

- 字段值为零值（空数组、空字符串、0、false）时，**JSON 里根本不会出现这个 key**。
- 前端如果没写 `|| []` / 可选链兜底，拿到 `undefined` 后做 `.map` / `.length` 就崩。

例如计划没有任务时 `tasks` 字段被 `omitempty` 去掉，前端 `plan.tasks.map(...)` 直接报错。这类问题只在“边界数据”（空列表、新建对象、未完成状态）下出现，happy path 测试永远发现不了。

## 二、本轮具体犯了哪些问题

### 2.1 响应 message 字段不全（最高频）

表现：

1. `InterviewResponse` / `InterviewDetail` 缺 `interview_id`、`score`、`total_questions`、`started_at`、`ended_at`、`current_question`、异步任务字段。
2. `QuestionDetail` 缺 `options_json` / `solution_json` / `judge_config_json` / `answer_template_json` / `answer`。
3. `PlanDetail` 缺 `industry_code`、`phase`、`phase_goal`、`start_date`、`end_date`、异步任务字段；`TaskDetail` 缺 `sort_order`、`due_date`。
4. `Community` 的 `PostSummary` / `PostDetail` 缺 `post_type`、`summary`、`tags`、`view_count`、`comment_count`、`author_avatar`、`updated_at`、`is_author`。

本质错误：定义 proto 时没有以“前端消费代码”为字段清单的来源。

直接后果：前端整片区域拿到 `undefined`，要么静默不渲染，要么 `.map`/`.length` 崩溃。

### 2.2 扁平 / 嵌套结构错配

表现：

1. 报告接口：后端扁平 `InterviewReport`，前端要 `{interview_id, status, report:{...}, duration_seconds, completed_at}` 外层包装。
2. 答题接口：后端扁平 feedback，前端要 `{feedback:{...}, next_question, is_finished}`。
3. 推荐接口：后端 `{questions:[...], reason}`，前端要 `{focus_tags, items:[{question:{...}, focus_tag, related_question_sets,...}]}`。
4. 社区作者：后端扁平 `author_*`，前端要嵌套 `author` 对象。

本质错误：proto 直接映射 biz 结构体，没有按前端的容器层级重新组织。

### 2.3 序列化形态不一致（CSV vs 数组、JSON 字符串 vs 对象）

表现：

1. `tags` 后端是 CSV 字符串，前端要 `string[]` 并 `.map`。
2. `solution_json` / `judge_config_json` / `answer_template_json` 后端是 JSON 字符串，前端要已解析的对象（`solution.summary`、`judge_config.evaluation_mode` 等直接取属性）。

本质错误：没有约定“在哪一层把存储形态转成消费形态”。

### 2.4 单字段消息被通用解包逻辑误折叠

表现：

1. `ListTTSConfigsResponse{ configs }` 这种单 repeated 字段消息，被网关的 `unwrapSingleListField` 折叠成裸数组，前端 `data.configs` 变 `undefined`。

本质错误：没意识到“通用响应归一化逻辑”会对单字段消息做特殊处理，新增这类接口时没检查它会不会被通用规则误伤。

### 2.5 `omitempty` 导致空值字段在边界场景消失

表现：

1. 空 `tasks`、空 `tags`、未设置的布尔标志，在零值时直接从 JSON 消失，前端缺兜底就崩。

本质错误：没把“空列表 / 新建对象 / 未完成状态”当成必须验证的输入。

## 三、本轮采用的修复手法（可复用范式）

修复分两条路径，按情况选用：

### 3.1 后端能直接提供 → 扩 proto + 填 service

当 biz / 域模型本来就有数据，只是没透出来：

1. 在 proto 的 response message 上补字段（注意字段号递增，不复用旧号）。
2. `buf generate` 重新生成。
3. 在 service 层填充新字段（从 biz 实体映射）。

例：`QuestionDetail` 补 `options_json` 等四个字符串字段；`PlanDetail` 补 `industry_code`、用 `CreatedAt + DurationDays` 算 `start_date`/`end_date`。

### 3.2 结构/形态需要重组 → Gateway 响应整形（BFF reshape）

当后端结构是扁平/CSV/JSON 字符串，而前端要嵌套/数组/对象，且这种转换是“纯展示适配、不含领域逻辑”时，放在 Gateway 的 `adaptLegacyResponseByPath` 里做：

- 报告 → 包一层 `report`；
- 答题 → 重组成 `{feedback, next_question, is_finished}`；
- 推荐 → 重组成 `{focus_tags, items:[...]}`；
- 社区 → 拼 `author` 嵌套对象、CSV `tags` 拆数组、补默认布尔；
- 计划 → 保证 `tasks` 恒为数组；
- TTS → 恢复 `{configs, providers, default_bindings}` 对象形态。

> **注意边界**：Gateway reshape 只能做“结构搬运、字段拆分/合并、默认值兜底”这类无领域语义的整形。一旦需要查库、算业务规则、判断权限，就必须回到对应服务的 service/biz 层（参见准则2 规则4：Gateway 只做协议转换，不持有业务逻辑）。本轮的 reshape 全部是纯结构转换，没有越界。

## 四、后续必须新增执行的专项规则

### 规则 1：定义/修改响应 message 前，先打开前端的消费代码

任何 `XxxResponse` / `XxxDetail` 的字段清单，权威来源是**前端对应的 TypeScript interface 和实际取值代码**，不是后端 biz 结构体。

编码前必须回答：

1. 前端这个页面/组件读了哪些字段？（搜 `data.xxx`、解构、`.map`、可选链）
2. 这些字段前端期望的**类型和结构**是什么？（数组？嵌套对象？已解析对象？）
3. proto 现在缺哪些、结构差在哪？

没有完成这步比对，不得提交 proto 改动。

### 规则 2：为每个对外接口写一张“契约对照表”

至少三列：

| 前端字段 (TS) | 前端期望类型/结构 | 后端来源 + 转换发生在哪一层 |
|---|---|---|

这张表能一次性暴露三类问题：缺字段、结构错配、形态不一致（CSV/JSON 字符串）。

### 规则 3：明确每个字段“在哪一层完成形态转换”

对每个需要变形的字段，写清楚：

1. 存储形态（DB / 域模型）：如 CSV 字符串、JSON 字符串。
2. 传输形态（proto）：通常保持后端原始形态透传。
3. 消费形态（前端）：数组、对象。
4. **转换点**：在 service 层转，还是在 Gateway reshape 层转？

禁止出现“两边都以为对方会转”而导致 CSV 原样塞给 `.map` 的情况。

### 规则 4：扁平/嵌套不一致时，明确 reshape 归属

- 纯结构搬运（包一层、拆作者对象、列表项重组）→ Gateway `adaptLegacyResponseByPath`。
- 需要领域数据/规则/权限 → 对应服务 service 层。

reshape 函数必须：按 path 精确匹配、对类型断言失败安全返回原值、覆盖“裸数组 / 对象 / 其它”多种上游形态。

### 规则 5：新增单字段 repeated 响应时，检查是否会被通用解包误伤

网关存在 `flattenPageResult` / `unwrapSingleListField` 这类通用归一化。新增形如 `Response{ repeated X items }` 的单字段消息时，必须确认：

1. 它会不会被折叠成裸数组？
2. 前端要的是裸数组还是带其它字段的对象？
3. 如果前端要对象，必须在 `adaptLegacyResponseByPath` 里加专项 case 还原结构（参考 TTS）。

### 规则 6：把“空值/边界数据”当成必测输入，对抗 omitempty

由于 proto 生成代码默认 `omitempty`，零值字段会从 JSON 消失。因此：

1. 前端对所有数组字段必须有 `|| []` 兜底，对象字段用可选链。
2. 后端/网关对“前端会无条件 `.map`/`.length`/解构”的关键数组字段，应在 reshape 层强制补空数组（如 `tasks`、`tags`、`items`、`configs`）。
3. 测试必须覆盖：空列表、新建未完成对象、初始状态。happy path 通过不代表边界通过。

### 规则 7：只改后端也要做前端侧验证

“只动了 proto 和 Go service”不是跳过前端验证的理由。合并前至少做其一：

1. 把网关实际输出的 JSON 与前端 interface 逐字段对照；
2. 跑前端 `tsc --noEmit`（注意区分本次相关报错与既有历史报错）；
3. 真实页面手动跑一遍关键路径，尤其是空数据/边界态。

### 规则 8：proto 字段演进只增不改号、不改义

补字段时：

1. 字段号严格递增，绝不复用历史号。
2. 不改已有字段的语义和类型。
3. 注释标明“对齐前端 XxxItem 的哪些字段”，方便后人回溯契约来源。

## 五、合并前的“契约闭环检查”清单

在准则2 第四节链路检查的基础上，针对前后端契约再加一组：

- 响应 message 字段清单 = 前端消费字段清单（无缺失）。
- 扁平/嵌套结构与前端期望一致（无错配）。
- CSV / JSON 字符串等形态，已在明确的某一层转成前端消费形态。
- 单字段 repeated 消息确认未被通用解包误折叠（或已加专项还原）。
- 关键数组/对象字段在空值/边界态下，前端有兜底或网关有补全。
- 已做前端侧验证（字段对照 / tsc / 手动跑页）。
- proto 字段号只增不复用，语义未改。

## 六、给后续开发者的直接结论

这轮问题的根因，一句话概括：

> **Proto 的响应结构被当成后端内部 DTO 来设计，而它其实是前后端之间的强契约；契约的字段清单和结构形态，唯一权威来源是前端的消费代码，不是后端手头有什么。**

四个最容易重犯的具体动作：

1. **先按 biz 结构体定 proto，后才想起前端要什么** → 缺字段。
2. **直接把域模型扁平结构透传** → 嵌套/扁平错配。
3. **把 DB 存储形态（CSV、JSON 字符串）原样发给前端** → `.map` / 属性访问崩溃。
4. **只验证 go build / go test 就宣布完成** → 漏掉前端这一侧，边界态白屏。

强制纪律：

> **没有以“前端消费代码”为依据完成字段对照、结构对齐、形态转换归属确认，并做过一次前端侧验证之前，不得宣布某个对外接口已完成。**
