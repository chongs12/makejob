# MakeJob 开发准则 2

> **文档目的**
>
> 本文不是替代 `docs/开发准则.md`，而是补充一份专门针对 **微服务迁移、Admin BFF、MQ 链路、跨服务契约、运行时配置** 的二次准则。
>
> 这些规则直接来自 2026-06-08 对 Phase 6 与补丁三阶段的复审修复经验。很多问题不是“不会写代码”，而是 **写代码时采用了错误的实现顺序、错误的边界假设、错误的验证深度**，导致代码在局部看起来成立，但放到整条链路里就失真。

---

## 一、这轮问题为什么会出现

### 1. 不是单点编码能力问题，而是“实现顺序”错了

这轮多数问题，并不是语法、框架或 Go 语言基本功错误，而是先写实现、后核对架构与契约，导致：

1. 先凭印象判断服务归属，再补代码。
2. 先让某个 RPC “能返回”，再考虑下游是否真实存在。
3. 先让 producer/consumer 两边各自完成，再核对 MQ payload 是否一致。
4. 先在 Admin 做“临时可用”的本地逻辑，再回头修正为真正的 BFF 委托。

这种顺序在单体里有时还能勉强收敛，但在微服务里会直接放大为：

- 契约漂移
- 服务边界漂移
- 状态机失真
- MQ 链路断裂
- 假成功
- 回归测试漏检

### 2. 不是没写逻辑，而是“把局部成立误当作全链路成立”

本轮多个问题都属于这个模式：

1. 某个 gRPC handler 返回了结构体，但字段没有全链路透传。
2. 某个 MQ 消费者能消费消息，但 producer 发的并不是它真正期望的 payload。
3. 某个 Admin 入口能返回结果，但返回结果并不来自权威服务。
4. 某个错误路径被“包装成成功响应”，从接口表面看像可用，实际上破坏上层判断。

根因是开发时只验证了“当前函数/当前服务”，没有验证“调用方 → service → biz → data → 下游/消息 → 回写”的闭环。

### 3. 微服务迁移里最容易犯的错：边界意识退化回单体思维

这次最典型的几个问题，都是单体思维残留：

1. 看到缺能力，就想在 Admin 本地补一点“近似实现”。
2. 看到下游不方便调用，就想直接靠本地表或近似字段解决。
3. 看到异步链路复杂，就想把失败立刻写成终态，省掉后续补偿。
4. 看到调试接口，就想“先返回个结果”，哪怕这个结果是伪成功。

这些做法在单体时代经常是小问题，但在微服务下会直接破坏：

- 服务所有权
- 权威数据来源
- 失败语义
- 重试语义
- 可观测性

### 4. 测试做了，但验证深度不够

本轮修复前，很多链路在“编译通过、单包测试通过”层面看起来没问题，但真实缺的是：

1. producer 与 consumer 的 payload 对照验证。
2. 受保护下游 RPC 的鉴权透传验证。
3. 终态前后重复回写的幂等验证。
4. Admin 作为 BFF 时，是否仍在偷持有本地域真相的验证。
5. 运行时配置更新后，是否传播到实际执行链路的验证。

结论很明确：**微服务里的问题往往不是“没写测试”，而是“没测对层次”。**

## 二、本轮具体犯了哪些问题

下面是这轮修复中暴露出的具体工程错误。

### 2.1 服务归属判断错误

表现：

1. 把本应属于 Admin 自有能力的 Scraper，错误理解成“等待独立 Scraper 微服务”。
2. 把本应由 RAG 服务负责的配置/索引管理，部分漂移成 Admin 本地兜底。
3. 把 AI 调试能力当成 Admin 直接可交付能力，而不是 AI Gateway 的下游能力。

本质错误：

- 在编码前没有先根据 `docs/microservice-redesign.md` 确认“谁拥有这个能力”。
- 以“哪里改起来快”代替“哪里才是权威归属”。

直接后果：

- 出现 `UNIMPLEMENTED` 残留。
- 出现 BFF 伪本地实现。
- 下游接口缺位时，上游仍然被误标记为已完成。

### 2.2 Proto / MQ 契约没有被当成唯一真相源

表现：

1. `scraper.import.questions` 的 producer 与 consumer 对 payload 字段理解不一致。
2. 同步候选题生成、Prompt 渲染、DebugAI 的字段在不同层之间有裁剪风险。
3. 任务状态回写用了通用字段，但没有先明确终态覆盖规则。

本质错误：

- 没有先列出“请求字段、响应字段、消息字段”的完整流向表。
- 写代码时默认“够用字段先传”，没有对照消费端/调用端逐项核查。

直接后果：

- 某些字段悄悄丢失。
- 某些字段只能在局部使用，无法跨服务闭环。
- Consumer 读到的并不是 Producer 真正表达的语义。

### 2.3 把 MQ 当成本地异步函数，而不是分布式状态机

表现：

1. Scraper 导入链路中，失败容易被直接写成终态。
2. 最终失败与单次失败没有清晰分层。
3. 回写接口没有明确“已终态不可覆盖”的保护。

本质错误：

- 没有先画 `pending -> running -> completed/failed` 状态机。
- 没有把“重试期内失败”和“重试耗尽后的最终失败”分开设计。

直接后果：

- 一次短暂失败就把任务永久打死。
- 重试成功后状态可能被旧失败覆盖。
- 重复消费、重复回写时语义不稳定。

### 2.4 BFF 漂移为伪领域服务

表现：

1. Admin 为了实现后台功能，容易回退成“自己拼一套结果”。
2. Admin 全量索引题目时，如果不谨慎，就会想直接借本地数据或非权威字段筛选。
3. Phase 6 中多个后台入口曾经出现“看似委托，实际上仍在本地判断/本地兜底”的情况。

本质错误：

- 没把 Admin 当成纯编排层，而是默认它可以暂时代持一部分领域知识。

直接后果：

- 服务边界再次模糊。
- 同一个业务事实在多个服务中出现两个版本。
- 后续修复时必须返工，把“本地真相”重新收口回权威服务。

### 2.5 权威标识与展示字段混用

表现：

1. 过滤题目、索引题目时，曾使用 `industry_code`、名称或其他近似字段代替权威 `industry_id`。
2. 跨服务索引或查询时，如果不用权威 ID，结果会出现偏差或误筛。

本质错误：

- 把“方便展示/方便输入的字段”当成“适合做权限、过滤、归属判断的字段”。

直接后果：

- 查询结果不精确。
- 后台统计和实际数据可能不一致。
- 隐蔽回归很难被 UI 层发现。

### 2.6 受保护下游调用的认证透传意识不足

表现：

1. Phase 6 中出现过 Admin 调用下游受保护 RPC 时，没有稳定透传服务令牌或用户令牌。
2. Question MQ 回写 Admin 状态时，也出现过鉴权上下文缺失。

本质错误：

- 把“本服务内已经鉴权过”误当成“跨服务调用无需再次构造认证上下文”。

直接后果：

- 本地调试可能能过，联调时却被下游拒绝。
- 异步链路因为没有用户请求上下文，更容易漏传令牌。

### 2.7 占位实现和假成功没有被严格禁止

表现：

1. AI Gateway `RenderPrompt` 曾把下游 LLM 错误包进成功响应。
2. 某些后台能力在下游未就绪时，容易留下“空结果/假成功/弱错误语义”。

本质错误：

- 过度追求“接口先能返回”。
- 没有把错误语义视作契约的一部分。

直接后果：

- 调用方误判成功。
- 前端和上游编排层无法做正确的失败分支处理。
- 日志看似正常，实际数据已偏离。

### 2.8 运行时配置设计只改“配置值”，没改“生效路径”

表现：

1. RAG `UpdateConfig` 早期容易停留在“配置改了”而不是“实际检索/索引/MQ 消费都切到新配置”。

本质错误：

- 把运行时配置当成普通表单存储，没有分析配置变更会影响哪些长生命周期对象。

直接后果：

- 配置接口返回成功，但真实执行仍在用旧模型、旧集合。
- 这是一种非常隐蔽的伪成功。

## 三、Phase 6 的反错误经验

Phase 6 的核心主题是 **Admin BFF 化、Gateway 去业务化、桥接层移除**。这一阶段最容易踩的坑，和后续补丁问题高度相关。

### 3.1 Admin 从“后台万能服务”收缩为“纯编排层”时，最容易半途而废

错误模式：

1. 名义上改成委托，实际上仍保留本地拼装、本地兜底、本地判断。
2. 为了赶进度，把本应由下游服务回答的问题留在 Admin。

反错误经验：

1. Admin 只能做聚合、映射、分页组合、权限编排。
2. 领域事实必须来自权威服务，不能在 Admin 再造一套。
3. 如果下游没有能力，Admin 应返回明确阻塞，不应伪实现。

### 3.2 Gateway 去桥接层后，不能把业务逻辑偷偷搬到别处

错误模式：

1. 表面删除 bridge，实际又在 handler 或 Admin 里补回局部业务逻辑。
2. 只关注路由是否注册，不关注路由背后是否真的连到正确服务。

反错误经验：

1. Gateway 只负责协议转换、鉴权、限流、流式代理。
2. 一条路由注册完成，不等于功能完成，必须验证“HTTP → Gateway → gRPC → 下游”的真实闭环。

### 3.3 Phase 6 最容易漏的是“下游鉴权透传”

错误模式：

1. 本地调用时直接拿已有 context 用，下游环境却要求明确 token。
2. MQ / SSE / 后台任务这类非用户直连链路，更容易忘记补服务认证。

反错误经验：

1. 所有跨服务 protected RPC，都必须明确写出认证来源：
   - 用户令牌透传
   - 服务令牌注入
   - 系统任务专用令牌
2. 这项规则必须在联调前用测试或手工验证覆盖一次。

### 3.4 Phase 6 最容易犯“字段能用就行”的错误

错误模式：

1. 用 `industry_code`、name、slug、title 之类展示字段做强约束过滤。
2. 用模糊字段替代权威外键。

反错误经验：

1. 展示字段只能展示，不能承担归属判断、权限判断、精确过滤。
2. 一旦跨服务，需要优先使用 ID、枚举、稳定 code 这类权威字段，并确认它们在各服务含义一致。

### 3.5 Phase 6 最容易低估“回写接口”的严肃性

错误模式：

1. 把任务状态回写当成内部小接口，没有设计幂等、终态保护和错误语义。
2. 认为“反正只有本服务会调”，就不做契约约束。

反错误经验：

1. 所有回写接口本质上都是状态机入口。
2. 只要会被 MQ consumer、后台 worker、SSE 轮询依赖，就必须当正式 RPC 设计。

## 四、后续必须新增执行的专项规则

以下规则用于补充 `docs/开发准则.md`，后续涉及微服务迁移和后台聚合开发时必须一并执行。

### 规则 1：先做“能力归属判定”，再写任何实现

编码前先回答：

1. 这个能力属于哪个服务拥有？
2. 当前服务是 owner、BFF、consumer，还是只是调用方？
3. 如果下游还没有这个能力，当前服务应阻塞、占位报错，还是完全不该开始？

未回答清楚这 3 个问题，不得开始写 handler。

### 规则 2：所有新增/修改 RPC，先画字段流向表

必须至少列清楚：

1. request 字段
2. response 字段
3. service → biz → data 的映射
4. 下游 gRPC 或 MQ payload 的映射
5. 终态回写字段

没有字段流向表，极易出现“局部字段有、全链路字段丢”的问题。

### 规则 3：所有 MQ 任务先画状态机，再写 producer/consumer

至少写清楚：

1. 初始状态
2. 开始处理状态
3. 重试中状态
4. 最终成功状态
5. 最终失败状态
6. 是否允许终态覆盖
7. 最终失败由谁写入

凡是跳过这一步的异步链路，后续大概率会出现伪终态、重复回写或重试污染。

### 规则 4：Admin 只能编排，不能持有领域真相

Admin 禁止：

1. 直接依赖其他服务数据库。
2. 在本地保存下游领域的“准真相”作为主要返回依据。
3. 用本地近似逻辑替代下游正式能力。

Admin 允许：

1. 调多个服务做聚合。
2. 做 DTO 映射和参数规范化。
3. 做后台任务发起与状态展示。

### 规则 5：所有 protected 下游调用必须显式标注认证来源

每个 client 方法旁边必须能回答：

1. 透传用户 token？
2. 注入服务 token？
3. 异步任务使用哪个系统 token？

如果答案不清楚，这个调用在联调时几乎一定会出问题。

### 规则 6：展示字段不能承担强约束语义

以下场景必须优先使用权威字段：

1. 所属关系判断
2. 精确过滤
3. 删除/更新范围控制
4. 跨服务同步
5. 向量索引主键/来源标识

禁止用 title、name、label、非稳定字符串承担这些职责。

### 规则 7：占位实现必须失败得明确、可监控、可移除

占位实现必须满足：

1. 返回明确错误码
2. 返回明确阻塞原因
3. 在文档/任务清单中标记阻塞点
4. 禁止返回空结构、空字符串、弱语义成功

### 规则 8：运行时配置必须定义“传播路径”

凡是支持运行时更新的配置，必须同时说明：

1. 配置存在哪里
2. 修改后影响哪些 usecase / client / consumer
3. 是否需要刷新长生命周期对象
4. 何时生效
5. 失败时如何回滚或拒绝更新

### 规则 9：每个新链路至少做一组“反向验证”

除了 happy path，至少还要验证：

1. 下游拒绝时，上游是否真实失败
2. MQ 重试后是否仍可成功
3. 已终态任务是否拒绝被旧消息覆盖
4. 缺 token 时是否正确失败
5. 配置变更后新请求是否真的用新配置

### 规则 10：合并前必须过“链路闭环检查”

至少确认：

- 架构归属正确
- Proto / MQ 契约一致
- service → biz → data 无字段丢失
- 权威数据来源正确
- 鉴权透传完整
- 异步状态机完整
- 占位实现无伪成功
- 测试覆盖 happy path + failure path + idempotency

## 五、给后续开发者的直接结论

这轮问题的根因，不应简单归纳成“开发者不细心”。

更准确的说法是：

1. **先实现、后校验架构边界**，导致能力归属漂移。
2. **先让接口能返回、后校验错误语义**，导致伪成功。
3. **先让两端都写完、后核对消息契约**，导致 MQ 断链。
4. **先做局部可用、后做全链路验证**，导致回归问题延后暴露。
5. **先按单体直觉补洞、后回到微服务权责**，导致 BFF 污染。

如果要避免重犯，核心不是“更认真一点”，而是强制执行下面这条纪律：

> **没有完成“归属判定 + 契约核对 + 状态机设计 + 鉴权路径确认 + 闭环验证”之前，不得宣布某个微服务能力已完成。**

这条纪律比任何局部编码技巧都更重要。
