# MakeJob 微服务改造补丁计划

> **文档用途**：为当前微服务改造遗留缺口设计一个可分三次执行的补丁计划。
>
> **适用范围**：仅覆盖以下三个优先级，不包含 Phase 7 运维事项。
> 1. Admin 自有 Scraper 能力补全
> 2. RAG 管理 RPC 与 Admin 委托补全
> 3. AI Gateway Admin 调试能力与 Admin 对接补全

---

## 一、执行前置约束

在执行任一阶段前，必须先阅读并遵守以下文档：

- `docs/microservice-redesign.md`
- `docs/tasks-phase1-7.md`
- `docs/task-execution-library.md`
- `docs/开发准则.md`
- `docs/补丁.md`（本文档）

执行时必须额外遵守以下约束：

1. **Proto 优先**：如果发现现有 Proto 与阶段目标不一致，必须先修改 Proto 并重生成代码，再进入业务实现。
2. **禁止伪成功**：依赖未就绪时可以返回 `ServiceUnavailable/UNIMPLEMENTED`，但一旦阶段开始落地，就不能继续保留假成功或空响应。
3. **保持架构边界**：
   - Scraper 属于 Admin 自有能力，不新建独立微服务。
   - RAG 配置/索引/文档管理属于 RAG 服务能力，Admin 仅作为 BFF 委托。
   - AI 调试/Prompt 渲染属于 AI Gateway 能力，Admin 仅作为 BFF 委托。
4. **同轮同步文档**：每完成一个阶段的代码实现，必须同步更新 `docs/改造任务清单.md` 和 `docs/补丁.md` 中对应阶段的状态与说明。
5. **验证不止编译**：每个阶段至少需要完成定向 `go test` / `go build`，以及一组跨层功能验证。

---

## 二、阶段划分总览

| 阶段 | 优先级 | 主题 | 目标结果 |
|------|--------|------|----------|
| 阶段一 | P0 | Admin Scraper 自有实现闭环 | 补齐 6 个 Scraper RPC，并打通 `scraper.import.questions` |
| 阶段二 | P1 | RAG 管理能力补全 | 补齐 RAG 5 个空壳 RPC，并恢复 Admin 的 RAG 管理入口 |
| 阶段三 | P2 | AI Gateway Admin 调试对接 | 补齐 AI Gateway admin RPC，并恢复 Admin 的 AI 调试/同步生成能力 |

**执行顺序不能调整**：

1. 阶段一先做，因为它是设计上明确属于 Admin 自有能力的遗漏，并且直接修复一条真实 MQ 断链。
2. 阶段二其次，因为它涉及 RAG 服务能力补全和 Admin 委托恢复，范围比阶段一更大。
3. 阶段三最后，因为它最依赖 Proto 契约校准，且涉及 AI Gateway 新增 admin 接口。

## 三、阶段一：Admin Scraper 自有实现闭环

### 3.1 阶段目标

按架构设计将 Scraper 实现为 **Admin 自有能力 + MQ 编排**，不再把它错误地标记为“等待 Scraper 微服务”。

完成后应满足：

- `GetScraperSources`
- `ScraperSearch`
- `ScraperFetch`
- `ScraperClean`
- `ScraperImport`
- `ScraperImportAsync`

全部在 Admin 内可用，并且异步导入能向 Question 服务投递 `scraper.import.questions` 任务。

### 3.2 设计依据

- `docs/microservice-redesign.md` 已明确 Scraper 归属为 `Admin 自有实现 + MQ`
- `docs/tasks-phase1-7.md` 的 Phase 6 没有覆盖这块
- 当前 `app/admin/internal/service/admin.go` 将上述 6 个 RPC 全部错误标成“等待 Scraper 微服务”

### 3.3 实现范围

**推荐改动文件**

- `app/admin/internal/biz/admin.go`
- `app/admin/internal/data/admin_repo.go`
- `app/admin/internal/data/model/` 下与 `scraper_sources` / `scraper_tasks` 相关模型
- `app/admin/internal/data/publisher.go`
- `app/admin/internal/service/admin.go`
- `pkg/mq/message.go`
- 如需补充配置：`app/admin/internal/conf/conf.go`、`app/admin/configs/config.yaml`
- 如需对导入任务消费格式做兼容修正：`app/question/internal/server/mq.go`
- 文档：`docs/改造任务清单.md`、`docs/补丁.md`

**推荐参考单体代码**

- `docs/backend/internal/service/scraper_service.go`
- `docs/backend/internal/service/scraper_service_test.go`
- `docs/backend/cmd/worker/main.go`

### 3.4 实现要点

1. **先确认数据模型**
   - 校验 `scraper_sources`、`scraper_tasks` 在 Admin 自有模型中是否完整。
   - 若字段与单体服务不一致，优先对齐最小必需字段，禁止在 service 层临时拼装状态。

2. **恢复 Admin 自有 Scraper 用例**
   - 在 `biz` 层定义 Scraper 源、抓取结果、清洗结果、导入请求、异步任务查询等领域结构。
   - 在 `data` 层恢复仓储实现，保持所有写操作走 repo，不允许 service 直写 DB。

3. **同步能力**
   - `GetScraperSources` 返回可用抓取源配置。
   - `ScraperSearch`、`ScraperFetch`、`ScraperClean` 先恢复单体已有能力。
   - 如果外部站点抓取依赖不足，必须清楚区分“源不可用”和“功能未实现”，不能统一糊成成功空结果。

4. **异步导入闭环**
   - `ScraperImport` 可先做同步导入到 Question。
   - `ScraperImportAsync` 必须创建 `scraper_tasks` 记录并投递 MQ。
   - MQ Payload 要与 Question 消费端真实格式一致。
   - Question 侧若当前只接受旧格式，需在本阶段一并兼容。

5. **任务状态机**
   - `pending -> running -> completed/failed`
   - 失败回写必须记录错误原因
   - MQ 重试与最终失败标记必须区分

6. **验收验证**
   - `go test ./app/admin/...`
   - `go test ./app/question/...`
   - `go build ./app/admin/cmd/server`
   - `go build ./app/question/cmd/server`
   - 验证一次异步导入请求能产生 `scraper_tasks` 记录和正确 MQ 消息

### 3.5 阶段一完成标准

- Admin 侧 6 个 Scraper RPC 不再返回 `ServiceUnavailable("UNIMPLEMENTED", ...)`
- `scraper.import.questions` 任务链路打通
- `ListScraperTasks` / `GetScraperTask` 能看到真实异步导入状态
- 文档已同步记录阶段完成情况

## 四、阶段二：RAG 管理能力补全

### 4.1 阶段目标

补齐 RAG 服务当前 5 个空壳管理 RPC，并恢复 Admin 对 RAG 管理能力的 BFF 委托。

本阶段重点补齐：

- `RAGService.DeleteIndex`
- `RAGService.GetConfig`
- `RAGService.UpdateConfig`
- `RAGService.TestConnection`
- `RAGService.GetDocumentStats`

以及恢复 Admin 侧对应入口：

- `TestRAGConnection`
- `IndexAllQuestions`
- `IndexQuestions`
- `DeleteRAGIndex`
- `SearchRAGQuestions`
- `SyncRAGDocumentsToVectorDB`
- `SyncAllPendingRAGDocuments`

并同步修复 Question → RAG 的事件发布缺口。

### 4.2 设计依据

- `docs/task-execution-library.md` 已把 RAG Proto 定义为 8 个 RPC
- `app/rag/internal/service/rag.go` 中后 5 个 RPC 当前为空壳
- `docs/microservice-redesign.md` 将 RAG 配置/索引/文档管理归属为 RAG 服务，Admin 只是委托层

### 4.3 实现范围

**推荐改动文件**

- `api/makejob/rag/v1/rag.proto`（仅当发现契约缺口时）
- `app/rag/internal/biz/`
- `app/rag/internal/data/`
- `app/rag/internal/service/rag.go`
- `app/rag/cmd/server/main.go`
- `app/admin/internal/biz/admin.go`
- `app/admin/internal/data/clients.go`
- `app/admin/internal/service/admin.go`
- `app/question/internal/data/`、`app/question/internal/biz/`、`app/question/internal/service/`
- `pkg/mq/message.go`
- 文档：`docs/改造任务清单.md`、`docs/补丁.md`

### 4.4 实现要点

1. **RAG 服务先补真实能力**
   - `DeleteIndex`：删除指定向量 ID / 文档 ID
   - `GetConfig` / `UpdateConfig`：统一 RAG 运行配置读取与更新
   - `TestConnection`：返回真实连接结果，禁止硬编码 `connected=true`
   - `GetDocumentStats`：返回真实集合/文档统计

2. **Admin 只做委托，不做伪本地实现**
   - 当前 `GetRAGConfigs/UpdateRAGConfigs` 若仍走 Admin 本地配置，需要明确是否与 RAG 服务合并管理。
   - 本阶段优先目标是恢复“RAG 相关管理操作通过 RAG 服务完成”，避免 Admin 再次漂移成自实现。

3. **补齐 Question → RAG 事件链**
   - 当前设计要求 Question 变更后推送 RAG 同步任务。
   - 必须检查题目创建、更新、删除路径是否真正发布了相应事件/任务。
   - 如果现有队列名与设计不一致，要先统一消息路径，再修逻辑。

4. **批量/全量索引策略**
   - `IndexAllQuestions` 可以由 Admin 拉取 Question 题目并批量调用 RAG `IndexQuestions`
   - 必须有失败明细或失败计数，不能仅返回布尔值

5. **文档同步策略**
   - `SyncRAGDocumentsToVectorDB`
   - `SyncAllPendingRAGDocuments`
   必须对接 RAG 服务的文档索引接口，不能继续停留在 Admin 本地占位

6. **验收验证**
   - `go test ./app/rag/...`
   - `go test ./app/admin/...`
   - `go test ./app/question/...`
   - `go build ./app/rag/cmd/server`
   - `go build ./app/admin/cmd/server`
   - 验证一次题目变更能触发 RAG 同步消息或索引调用

### 4.5 阶段二完成标准

- RAG 服务 5 个空壳 RPC 均改为真实实现
- Admin 的 RAG 管理入口不再返回 `UNIMPLEMENTED`
- Question → RAG 同步链真实可触发
- RAG 配置、连接测试、索引删除、文档统计具备真实响应

## 五、阶段三：AI Gateway Admin 调试对接

### 5.1 阶段目标

补齐 AI Gateway 缺失的 Admin 调试能力，并恢复 Admin 的以下入口：

- `GenerateQuestionPipeline`（同步入口）
- `TestRenderPrompt`
- `DebugAI`

本阶段的关键不是直接写 handler，而是先 **校准契约**：确认这些 Admin 能力在架构上如何落到 AI Gateway。

### 5.2 设计依据

- 当前 Admin 这 3 个入口都因为“等待 AI Gateway admin RPC”而不可用
- `docs/microservice-redesign.md` 对 AI Gateway 主要定义了 Agent RPC，没有完整覆盖 Admin 调试接口
- 阶段三本质上是“补设计缺口 + 补实现”

### 5.3 契约决策建议

本阶段建议先做以下设计收敛，再编码：

1. **Prompt 渲染调试**
   - 在 AI Gateway 新增“模板渲染预览”RPC
   - 输入：模板、变量、场景、行业、模型参数
   - 输出：渲染后的 prompt、变量解析明细、可选的试跑结果

2. **AI 调试**
   - 在 AI Gateway 新增“通用调试”RPC
   - 输入：provider/model/runtime config/messages/scene
   - 输出：模型原始响应、结构化响应、token 用量、耗时、错误信息

3. **同步题目流水线**
   - 不建议继续把同步 `GenerateQuestionPipeline` 留成“等待 AI Gateway”却没有清晰下游。
   - 本阶段必须先决定两种方案之一：
     - 方案 A：实现 AI Gateway 的同步候选题生成 RPC，Admin 同步调用后直接返回候选题
     - 方案 B：把同步入口显式改为基于现有异步流水线的包装能力
   - 推荐 **方案 A**，因为它最符合“AI 调试/预览”类后台能力。

### 5.4 实现范围

**推荐改动文件**

- `api/makejob/ai_gateway/v1/ai_gateway.proto`
- 相关生成文件 `*.pb.go`、`*_grpc.pb.go`
- `app/ai_gateway/internal/biz/`
- `app/ai_gateway/internal/service/ai_gateway.go`
- `app/ai_gateway/cmd/server/main.go`
- `app/admin/internal/biz/admin.go`
- `app/admin/internal/data/clients.go`
- `app/admin/internal/service/admin.go`
- 如需 Gateway/前端兼容映射，检查 `app/gateway/internal/proxy/handler.go`
- 文档：`docs/改造任务清单.md`、`docs/补丁.md`

### 5.5 实现要点

1. **先补 AI Gateway admin Proto**
   - 本阶段不得在没有下游 Proto 的情况下硬写 Admin 假调用
   - 新增 RPC 命名要清晰区分业务 Agent RPC 与 Admin 调试 RPC

2. **Prompt 渲染必须是真渲染**
   - 不能只返回模板原文
   - 必须体现变量替换后的结果
   - 如包含模型试跑，必须区分“仅渲染”和“渲染 + 调用”

3. **DebugAI 必须保留可观测信息**
   - request / rendered prompt / response / token / latency / error
   - 不能只返回一段文本

4. **同步题目流水线要避免与已有异步链冲突**
   - `GenerateQuestionPipelineAsync` 继续走 Admin → MQ → Question
   - `GenerateQuestionPipeline` 作为后台同步预览/候选生成入口
   - 二者职责必须区分清楚

5. **验收验证**
   - `go test ./app/ai_gateway/...`
   - `go test ./app/admin/...`
   - `go build ./app/ai_gateway/cmd/server`
   - `go build ./app/admin/cmd/server`
   - 验证一次 Prompt 渲染调试、一次 AI 调试调用、一次同步候选题生成

### 5.6 阶段三完成标准

- AI Gateway 存在明确的 Admin 调试 Proto 与实现
- Admin 的 `TestRenderPrompt`、`DebugAI` 不再返回 `UNIMPLEMENTED`
