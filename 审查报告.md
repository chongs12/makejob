### 5. 综合评估

| 项目 | 结论 |
| --- | --- |
| 原报告“功能覆盖率约 30-40%” | 仍大体准确；按可替代单体的前端/外部业务能力衡量，当前更接近 `35%`，不建议上调。 |
| 仅按 proto 方法数量粗算会得到什么 | 当前仓库共有 `145` 个 proto RPC，其中服务端方法实装约 `119` 个，表面实现率约 `82%`；但这个数字被 `admin` 的 75 个 RPC 和大量 bridge 委托严重放大，不能代表真实业务覆盖率。 |
| 为什么不是按 proto 已实现率计算 | 因为默认 bridge 使前端并不真正走微服务；同时大量关键能力要么未写入 proto，要么虽有 proto 但只是桩/简化版/bridge 委托。 |
| 优先级最高缺口 | 1. 先解决 Gateway 默认 bridge 与非 bridge 路由残缺问题，否则“微服务可用性”无法成立。 |

|  | 5. 将 `ai`、`industry`、RAG、Scraper、TTS/ASR 等仍依赖 bridge 的运行时能力真正拆出。 |

  四、核心问题总结

  问题 1：Bridge 模式使微服务形同虚设

  Gateway 在配置了数据库时走 Bridge 模式，完全绕过所有微服务。当前微服务实际上不会被调用。

  问题 2：大量 Proto RPC 有定义无实现

  - Interview：9/14 个 RPC 未实现
  - Growth：5/8 个 RPC 未实现
  - Community：2/8 个 RPC 未实现 + 1 个未实现
  - Question：RunCode 桩实现

  问题 3：已实现方法功能大幅缩水

  - Growth 的 GrowthSummary 和 WeeklyFocus 返回数据大幅简化
  - Community 的所有方法都缺少富字段和业务校验
  - StudyLog 数据模型不兼容

  问题 4：核心业务能力完全缺失

  实时语音面试、代码执行、RAG 检索、TTS/ASR、异步任务处理、AI 运行时等单体的核心差异化能力，在微服务中均无独立实现。

  问题 5：存在实现 Bug

  - User 微服务的 RefreshToken 未正确生成
  - User 微服务的 Login/Register 未填充 refresh_token 字段

  ---
  五、结论

  当前微服务改造处于早期阶段，功能覆盖率约 30-40%。 实际情况是：

  1. 只有 Learning Archive 是完整且有增量的微服务
  2. Admin 微服务最完整（~65 RPC），但大量逻辑通过 bridge 委托给单体
  3. User 微服务基本可用，有 1 个 Bug
  4. Question 微服务缺失代码执行、考试、题集、错题专题
  5. Interview 微服务仅实现 CRUD，核心的面试流程（结束/报告/语音/编程）全部缺失
  6. Growth 和 Community 微服务是单体的大幅简化版
  7. 11 个功能模块完全没有独立微服务，依赖 bridge 运行

  如果要真正实现微服务化，需要：优先补齐 Interview 的核心流程（FinishInterview/GetReport）、Question 的 RunCode、以及将
  AI/TTS/RAG 等基础设施从 bridge 中剥离为独立服务。
