数据流深度分析报告

1. 刷题记录如何影响学习计划和成长档案

  数据写入链路

    当用户提交答案时，question_service.go:SubmitAnswer() 执行以下操作：

      1. 判分：judgeAnswer() 根据题型（单选/多选/编程/主观）判定 isCorrect
      2. AI 分析（编程题/主观题）：调用 quizAnalyzer.AnalyzeCode() 获得 CodeAnalysis，其中包含 MistakeTags、StrengthTags、Improvements
      3. 保存答题记录：写入 user_question_records 表（字段：user_id, question_id, user_answer, is_correct, time_spent, analysis_json）
      4. 同步写入学习档案：syncPracticeLearningArchive() 将错因标签写入 learning_archive_entries 表

    关键代码位置：
      - question_service.go:475-561 — SubmitAnswer() 主流程
      - question_service.go:1148-1190 — syncPracticeLearningArchive() 将练习结果沉淀到 learning_archive_entries

    learning_archive_entries 表是跨模块共享的核心中间表，字段包括：
      - source_type = "practice_question" | "interview_coding" | "plan_task_feedback"
      - mistake_tags_json — JSON 数组，如 ["边界条件生疏", "状态定义不清"]
      - strength_tags_json、suggestions_json

  对成长档案的影响

    growth_service.go:GetGrowthSummary() 直接读取：
      - recordRepo.GetUserStats() — 从 user_question_records 统计总题数、正确率
      - learningArchiveRepo.ListRecentByUser() — 从 learning_archive_entries 拉取最近条目
      - 调用 buildTrainingFocusSignals() 聚合错因标签，生成 FocusSignals（高频错因排名）

  对学习计划的影响

    plan_service.go:GeneratePlan() 中：
      - 调用 buildLatestPlanFocusSignals() 读取 learning_archive_entries + mock_interviews
      - 将高频错因合并到 UserProfile.WeakTopics，传给 AI 生成计划
      - 计划的 plan_json 中持久化了 focus_signals，供后续任务解释使用

  数据流：
    刷题 SubmitAnswer → user_question_records + learning_archive_entries
                             ↓                    ↓
                       growth_service       plan_service.GeneratePlan
                       (GetGrowthSummary)   (buildLatestPlanFocusSignals → WeakTopics → AI)

2. 面试评价如何同步到成长档案

  面试报告存储

    interview_service.go:FinishInterview() 执行：
      1. 调用 interviewAgent.GenerateReport() → 返回 ai.InterviewReport 结构体
      2. 调用 enrichInterviewReportWithCoding() 为编程题补充 CodingQuestionDiagnosis（含 MistakeTags、StrengthTags）
      3. 序列化为 JSON 存入 mock_interviews.report_json 字段
      4. 更新 mock_interviews.score 和 mock_interviews.ai_feedback（摘要文本）

    存储形式：完整的 InterviewReport JSON，包含 overall_score、dimension_scores、weaknesses、suggestions、coding_diagnostics（含每题的 mistake_tags）。

  同步到学习档案

    interview_service.go:persistLearningArchiveEntries() 在面试结束时：
      - 遍历 report.CodingDiagnostics
      - 每道编程题的 MistakeTags + StrengthTags + Suggestions 写入一条 learning_archive_entries 记录
      - source_type = "interview_coding"
      - source_ref = "interview:{id}:question:{index}"

    关键代码：interview_service.go:845-891

  成长档案如何消费

    growth_service.go:GetGrowthSummary() 和 GetWeeklyFocus() 都调用 buildTrainingFocusSignals(entries, interviews, limit)，该函数：
      1. 从 learning_archive_entries 提取 mistake_tags_json 统计错因频率（collectArchiveFocusSignalSeeds）
      2. 从 mock_interviews.report_json 解析 weaknesses 统计面试薄弱项频率（collectInterviewFocusSignalSeeds）
      3. 合并排序，取 Top N 生成 trainingFocusSignal

  数据流：
    面试 FinishInterview → mock_interviews.report_json + learning_archive_entries (source_type=interview_coding)
                                ↓                        ↓
                          growth_service             growth_service
                          (GetGrowthSummary)         (GetWeeklyFocus)
                          读 report_json 统计        读 archive_entries 统计
                                ↓
                          buildTrainingFocusSignals → FocusSignals + TrendSummary

3. 学习计划生成时如何参考用户历史数据

  GeneratePlan 链路

    plan_service.go:GeneratePlan() 的关键步骤：

      1. 构建用户画像：调用 buildLatestPlanFocusSignals(ctx, userID, industryID, industryCode)
        - 读取 learning_archive_entries（最近 24 条，按行业过滤）
        - 读取 mock_interviews（最近 5 条，按行业过滤）
        - 调用 buildTrainingFocusSignals() 聚合高频错因
      2. 合并弱项：mergePlanProfileWeakTopics(req.WeakTopics, focusSignals) 将用户显式弱项与系统识别的高频错因合并
      3. 传给 AI：UserProfile.WeakTopics 包含所有弱项，注入到 prompt 的 {{weak_topics}} 变量
      4. 持久化上下文：planStoredContext.FocusSignals 存入 plan_json，供后续任务解释和调整使用

  AdjustPlan 链路

    plan_service.go:AdjustPlan() 额外参考：
      - loadPlanAdjustmentDecision() 读取 learning_task_diagnoses 表中的诊断结果
      - 诊断结果来自用户提交任务反馈后异步生成的 taskFeedbackDiagnosisResult
      - PlanAdjustmentInput 包含 WeakTopics、ActionSummaries、ReasonCodes、PhaseBlueprint

  数据来源：
    - learning_archive_entries — 刷题和面试的错因归档
    - mock_interviews — 面试报告的薄弱项
    - learning_task_diagnoses — 计划任务反馈的诊断结果（异步生成）
    - 用户手动填写的 WeakTopics 和 GoalDescription

  数据流：
    learning_archive_entries ──┐
                               ├──→ buildLatestPlanFocusSignals → focusSignals
    mock_interviews ───────────┘           ↓
                                    mergePlanProfileWeakTopics
                                           ↓
    用户填写 WeakTopics ────────→  UserProfile.WeakTopics → AI GeneratePlan
                                                                    ↓
                                                         plan_json (含 focus_signals)
                                                                    ↓
    learning_task_diagnoses ────→ AdjustPlan → AI 调整计划

4. AI 陪伴模块是否了解用户当前的学习状态

  陪伴聊天的 prompt 构建

    companion_service.go:Chat() 调用 normalizeCompanionMessages()，其中：

      1. 前端传入的 context：buildCompanionContextMessage(req.Context) 将前端传入的 context map 格式化为系统消息，如 "当前学习陪伴上下文：\n- plan_title: xxx\n- focus_task: yyy"
      2. 后端 system prompt：companionAgent.Chat() 中通过 promptResolver 解析模板，模板变量仅有 {{user_emotion}} 和 {{latest_user_message}}

    关键发现：后端陪伴 Agent 的 system prompt 不包含用户的薄弱知识点、最近面试结果等学习状态。学习状态完全依赖前端通过 context 字段传入。

  前端侧（companionHubHelpers.ts 中）：
    - persistCompanionPlanContext() 将成长页的 focus signals、当前计划信息存入 localStorage
    - 发起聊天时从 localStorage 读取并放入 context 字段

  数据流：
    成长页/计划页 → persistCompanionPlanContext() → localStorage
                                                          ↓
    CompanionWorkspacePage → sendCompanionChatRequest({ context: {plan_title, focus_task, ...} })
                                                          ↓
    companion_service.go → buildCompanionContextMessage(context) → system message
                                                          ↓
                                                  companionAgent.Chat(messages)

  结论：陪伴模块了解用户当前学习状态，但数据来源是前端 localStorage 传递，后端不主动查询用户历史。如果前端未传 context，陪伴 Agent 对用户学习状态一无所知。

5. AI 面试出题如何利用题库和成长档案

  面试出题链路

    interview_service.go:CreateInterview() → interviewAgent.StartInterview() → generateQuestion()

    在 runtime/interview_agent.go:generateQuestion() 中：
      - system prompt 仅包含面试角色设定（基于 prompt_templates 表的场景模板）
      - user prompt 包含：行业、难度、候选主题、已出题列表
      - 不包含用户的刷题历史、成长档案、上次面试弱点

    buildQuestionUserPrompt() 的内容：
      请生成第 X/Y 道面试题。
      行业: go
      难度要求: medium
      候选主题: 基础语法、并发编程、工程实践、性能优化
      已出题列表: ...

  题库使用方式

    面试出题完全由 AI 实时生成，不从 questions 表抽取。InterviewAgent 与 QuestionRepository 之间没有依赖关系。

  成长档案的利用

    面试模块不读取 learning_archive_entries 或 user_question_records。interviewService 的依赖注入中虽然有 learningArchiveRepo，但仅用于面试结束时写入（persistLearningArchiveEntries），不用于出题时读取。

  数据流：
    CreateInterview → interviewAgent.StartInterview
                            ↓
                      generateQuestion(config)
                            ↓
                      system prompt (角色设定) + user prompt (行业/难度/主题/已出题)
                            ↓
                      AI 实时生成题目 ← 不读取题库、不读取成长档案

  结论：面试出题未利用题库和成长档案。题目由 AI 根据行业/难度/主题实时生成，不考虑用户的刷题历史或上次面试弱点。

存在的数据孤岛与问题

1. 面试出题与用户画像完全隔离
  面试出题不读取 learning_archive_entries 或 user_question_records，无法针对用户薄弱点出题。这是一个明确的功能缺失。

2. 陪伴模块对学习状态的感知依赖前端传递
  后端 companionAgent.Chat() 的 system prompt 不包含任何用户学习数据。如果前端未传 context，陪伴 Agent 完全不了解用户状态。建议后端主动查询 learning_archive_entries 和当前计划状态注入 prompt。

3. 题库与用户画像之间无标签匹配机制
  questions 表有 tags 字段，learning_archive_entries 有 mistake_tags_json，但练习推荐（GetPracticeRecommendations）使用的是关键词搜索（expandPracticeFocusTagKeywords），不是基于结构化标签的精确匹配。题库的 tags 与错因标签体系之间没有建立映射关系。

4. 成长档案与面试报告的 weaknesses 有重复解析
  growth_service.go 中 collectInterviewFocusSignalSeeds() 每次都重新解析 mock_interviews.report_json，而 learning_archive_entries 中已经存储了面试编程题的错因标签。两者存在数据冗余，且非编程题的面试薄弱项（来自 report.Weaknesses）只有 report_json 一条路径，没有写入 learning_archive_entries。

5. 无事件机制，全靠同步写入 + 实时查询
  整个系统没有消息队列或事件总线。模块间耦合方式为：写入方直接调用 learningArchiveRepo.Upsert()，消费方实时查询。这种模式在当前规模下可行，但如果未来需要异步解耦（如成长档案缓存预计算），需要引入事件机制。
