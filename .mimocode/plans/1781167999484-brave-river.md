# AI 题卡生成流水线修复计划（对齐单体实现）

## 概述

当前微服务版 AI Gateway 的题卡生成流水线与原始单体实现存在 14 处字段/行为级差异。本计划逐项修复，使微服务版行为与单体完全一致。

---

## 已验证的 14 处差异（Gap）

| # | 差异点 | 当前 ai_gateway | 单体实现 | 涉及文件 |
|---|--------|-----------------|----------|----------|
| 1 | `buildCodeJudgeConfigSkeleton` 默认值 | `time_limit_ms=5000`, `memory_limit_mb=256`, `reference_solutions=[]`, `starter_code=""` | `time_limit_ms=2000`, `memory_limit_mb=128`, 从 card.Answer 填充 reference_solutions, 按语言生成 starter_code 模板 | `pipeline_repair.go:278` |

| 3 | `normalizeCodeField` 缺少污染清理 | 仅去除 code fence | 去除 code fence 后还调用 `trimQuestionPipelineEmbeddedPayload` | `pipeline_repair.go:233` |
| 4 | 缺少卡片约束强制执行 | 仅按 title 做去重（`question_pipeline.go:576-582`） | `dedupeQuestionPipelineCards` (title+answer 复合 key + 按 confidence 排序), `filterQuestionPipelineCardsByIntent`, `enforceQuestionPipelineCardConstraints` | `question_pipeline.go` |

## 额外发现：Stream 路径参数缺失

除了上述 14 gap，还发现 **Stream 路径未传递 `generationMode`/`includeScraped`/`includeGenerated`/`sources`** 四个参数：

- Admin biz 接口 `GenerateQuestionCandidatesStream` 签名仅 5 个参数（`admin.go:138`）
- Admin data 实现仅设置 4 个 proto 字段（`clients.go:521-526`）
- AI Gateway service 层仅提取 4 个参数（`ai_gateway.go:329-335`）

**建议在 Step 2/3 中一并修复此不对称**，否则 Stream 路径永远丢失这些参数。

## 实施步骤

### Step 1: Proto — 新增 `industry_name` 和 `categories` 字段

**文件**: `api/makejob/ai/v1/ai.proto`

在 `GenerateQuestionCandidatesRequest` message（~line 178）末尾新增：
```protobuf
string industry_name = 9;
repeated string categories = 10;
```

执行 `buf generate` 重新生成 Go 代码。

### Step 2: Admin Service — 加载行业+分类并传递下游

**文件清单**:
- `app/admin/internal/service/admin.go`
- `app/admin/internal/biz/admin.go`
- `app/admin/internal/data/clients.go`

**改动**:

1. **`admin.go` `GenerateQuestionPipeline()`（~line 272）和 `GenerateQuestionPipelineStream()`（~line 328）**:
   - 调用 AI Gateway 前，加载行业: `s.uc.GetIndustryByCode(ctx, normalized.GetIndustryCode())`
   - 加载分类: `s.uc.ListCategories(ctx)`，按 `industry.ID` 过滤
   - 提取 `industry.Name` 和分类名称 `[]string`
   - 传递 `industryName` 和 `categories` 到 AI Gateway 客户端调用

2. **`admin.go` `normalizeQuestionPipelineRequest()`（~line 1870）**:
   - 默认 `candidate_count` 从 `5` 改为 `8`（对齐单体 `defaultQuestionPipelineCount`）

3. **`biz/admin.go` `AIGatewayClient` 接口（~line 130）**:
   - `GenerateQuestionCandidates` 签名新增 `industryName string, categories []string`
   - `GenerateQuestionCandidatesStream` 签名新增 `industryName string, categories []string`
   - **（额外）** `GenerateQuestionCandidatesStream` 签名还需新增 `generationMode string, includeScraped bool, includeGenerated bool, sources []string` 以修复 Stream 路径参数缺失

4. **`data/clients.go`**:
   - `GenerateQuestionCandidates()`（~line 444）: 设置 `IndustryName` 和 `Categories`
   - `GenerateQuestionCandidatesStream()`（~line 505）: 设置 `IndustryName`、`Categories` 以及新增的 `GenerationMode`、`IncludeScraped`、`IncludeGenerated`、`Sources`

### Step 5: 核心流水线 — 修复 question_pipeline.go 中的 8 处 gap

**文件**: `app/ai_gateway/internal/biz/question_pipeline.go`

#### Gap 5 — `buildConstraintSummary` 兜底约束（~line 176）
在 `return` 前追加:
```go
parts = append(parts, "如果无法满足约束，宁可少输出，也不要补无关题凑数。")
```

#### Gap 6 — `extractLanguageCounts` 支持中文数字（~line 105）
替换 regex 为单体版本:
```go
re := regexp.MustCompile(`(?i)(?:必须|至少|恰好|其中必须有|其中有|至少有|确保有)?\s*([0-9一二两三四五六七八九十]+)\s*(?:个|道|张)?(?:题|题卡)[^。\n]{0,12}?(?:是|为)?\s*(java|go|golang)`)
```
新增 `parseQuestionPipelineCountToken()` 函数（支持中文数字 一~十）。

#### Gap 7 — `industryName` 使用传入参数（~line 485）
```go
// 之前: industryName := industryCode
// 改为直接使用传入的 industryName 参数
```

#### Gap 8 — `categories` 使用传入参数（~line 488）
```go
// 之前: categories := make([]string, 0)
// 改为直接使用传入的 categories 参数
```

#### Gap 9 — 运行时覆盖参数（~line 347，在 LLM 调用前）
根据 `constraints.RequireCode` 和是否 compact 模式，覆盖 `cfg` 的 `MaxTokens` 和 `Temperature`:
- Compact + code: MaxTokens=2600, Temperature=0.2
- Compact + 非code: MaxTokens=1400, Temperature=0.4
- 非Compact + code: MaxTokens=3200, Temperature=0.35
- 非Compact + 非code: MaxTokens=1800, Temperature=0.5

#### Gap 10 — Mock Provider 检测（LLM 响应后，~line 353）
新增 `isPipelineMockOutput()` 函数，检测三个标记字符串。在 `generateSingleCard` LLM 响应后调用，如检测到则设置 `FailureStage = "provider"` 并返回错误。

#### Gap 11 — 卡片默认值（`generateSingleCard` 返回前）
新增 `applyPipelineCardDefaults()` 函数:
```go
Confidence:  0.94
SourceType:  "generated"
SourceLabel: "AI 智能体生成"
SourceTitle: "智能体候选题卡"
```

#### Gap 4 — 卡片约束强制执行（卡片 append 后，~line 605）
在 `cards = append(cards, card)` 之后:
1. `dedupeQuestionPipelineCards()` — 按 title+answer 复合 key 去重，按 confidence 排序
2. `filterQuestionPipelineCardsByIntent()` — 过滤项目类卡片
3. `enforceQuestionPipelineCardConstraints()` — 强制执行 code 类型、GoFeatureOnly、项目排除等约束

### Step 6: 修复 pipeline_repair.go 中的 6 处 gap

**文件**: `app/ai_gateway/internal/biz/pipeline_repair.go`

#### Gap 12 — 新增 `trimQuestionPipelineEmbeddedPayload`
移植单体实现（`admin_question_pipeline.go:936-955`），检测并截断污染标记。

#### Gap 2 — 增强 `sanitizeQuestionCandidate`（~line 410）
替换简单 TrimSpace 为:
- content/explanation: 调用 `trimQuestionPipelineEmbeddedPayload`
- code 类型 answer: 调用 `normalizeCodeField`
- 非 code 类型 answer: 调用 `trimQuestionPipelineEmbeddedPayload`
- solution: code 类型调用 `trimQuestionPipelineEmbeddedPayload`，非 code 类型仅 TrimSpace

#### Gap 3 — 增强 `normalizeCodeField`（~line 233）
去除 code fence 后，追加调用 `trimQuestionPipelineEmbeddedPayload`。

#### Gap 1 — 修复 `buildCodeJudgeConfigSkeleton`（~line 278）
- `reference_solutions`: 从 `card.Answer` + `card.Solution` 填充
- `starter_code`: 使用语言模板（新增 `buildDefaultStarterCode()`）
- `time_limit_ms`: 5000 → 2000
- `memory_limit_mb`: 256 → 128

#### Gap 13 — 修改 `normalizeCodeSolution` 签名（~line 251）
改为 `(solution string, judgeConfig any) string`，solution 为空时从 `judgeConfig.ReferenceAnswers[0].Explanation` 兜底。

#### Gap 14 — 新增 `normalizeCodeJudgeConfig`
移植单体实现（`admin_question_pipeline.go:3230-3270`），规范化 judge_config map。

#### 补充 — 更新 `buildSingleCardRepairSchema` 默认值
`time_limit_ms`: 5000 → 2000, `memory_limit_mb`: 256 → 128。

- `isPipelineMockOutput()` — Mock 检测

同时更新 `buildTargetLanguageLabel()`（~line 202）返回描述性语句:
```go
func buildTargetLanguageLabel(language string) string {
    switch strings.TrimSpace(language) {
    case "go":   return "本轮必须生成 Go 语言特性或 Go 核心机制相关题卡。"
    case "java": return "本轮必须生成 Java 相关题卡，用于满足显式语言配额。"
    default:     return "未指定单独语言配额，本轮遵循整体需求与智能体指令。"
    }
}
```

## 验证方案

1. **单元测试**: 为每个新增/修改函数编写测试
2. **集成测试**: Mock LLM client，运行完整流水线，验证:
   - industry_name + categories 出现在 prompt 中
   - 运行时覆盖生效（正确的 temperature/tokens）
   - JudgeConfig skeleton 有填充的 reference_solutions + starter_code
   - 卡片获得 Confidence=0.94, SourceLabel="AI 智能体生成"
   - content/answer 字段的嵌入污染被清理
   - Mock output 被检测并失败
   - 重复卡片按 title+answer 去重
   - 语言聚焦时项目卡片被过滤
3. **端到端测试**: 调用 admin gRPC 端点，验证流式事件逐张推送正确字段的卡片
4. **手动测试**: 在后台管理页面点击"生成题卡"，验证卡片逐张弹出且字段正确
