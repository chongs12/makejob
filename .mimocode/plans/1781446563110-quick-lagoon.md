# AI 功能 500 错误分析报告

## 问题描述

所有通过 gRPC 调用 AI Gateway 的功能（面试、学习计划、陪伴聊天、答题分析、简历解析、Live2D）均返回 HTTP 500，但 **AI 流水线生成题卡功能正常工作**。

## 架构链路

```
正常AI功能:  Frontend → Gateway(Gin) → Interview/Companion/Plan(gRPC) → AI Gateway(gRPC:9011) → ARK LLM(HTTP)
流水线功能:  Frontend → Gateway(Gin) → Admin(gRPC)                     → AI Gateway(gRPC:9011) → ARK LLM(HTTP)
```

## 根因分析

### 核心差异：Context 处理方式不同

**流水线（正常）** — `question_pipeline.go:424`
```go
llmCtx, cancel := context.WithTimeout(context.Background(), 3*time.Minute)
resp, err := uc.llm.Chat(llmCtx, messages, &effectiveCfg)
```
- 创建**完全独立**的 context，与上游 gRPC context 无关
- 即使上游 context 被取消，LLM 调用仍可正常完成

**其他AI功能（失败）** — `ai.go:153`
```go
resp, err := uc.llm.Chat(ctx, messages, cfg)
```
- 直接传递 gRPC handler 的 context
- 在 `ark_client.go:75` 中首先检查 `ctx.Err()`
- 虽然 `buildLLMRequestContext` 使用 `context.WithoutCancel` 创建独立超时，但 **`ctx.Err()` 检查在 `WithoutCancel` 之前执行**

### 超时传播链分析

| 层级 | 配置超时 | 实际效果 |
|------|---------|---------|
| Gateway (Gin HTTP) | `timeout: 10s` (config) | Gin 默认无 per-request 超时，`r.Run()` 未应用此配置 |
| Interview gRPC Server | `timeout: 3m` (config) | 代码 fallback 也是 3min |
| AI Gateway gRPC Server | `timeout: 60s` (config) | **实际生效 60s** |
| LLM HTTP Client | `120s` (hardcoded) | 通过 `WithoutCancel` 独立 |

**关键发现**: AI Gateway gRPC server 的 `timeout: 60s` 配置会通过 Kratos 中间件注入到 context deadline 中。当 Interview 服务的 gRPC 请求到达 AI Gateway 时，context 已携带来自上游的 deadline。

### 最可能的失败路径

1. Interview 服务调用 AI Gateway 的 `InterviewAgent` RPC
2. AI Gateway handler 收到 ctx（可能携带上游较短的 deadline）
3. `InterviewAgentUseCase.GenerateQuestion()` 调用 `uc.llm.Chat(ctx, ...)`
4. `Chat()` 第一行检查 `ctx.Err()` → 如果 ctx 已被取消或 deadline 已过 → **立即返回 `ServiceUnavailable`**
5. Interview 服务收到错误 → 包装为 `InternalServer("AI_CALL_FAILED")` → HTTP 500

### 为什么流水线不受影响

流水线在 `generateSingleCard` 中使用 `context.WithTimeout(context.Background(), 3*time.Minute)`，完全忽略上游 context，所以不受任何上游超时或取消的影响。

## 潜在根因排序（按可能性）

### 1. 上游 Context 超时/取消传播（最可能）
- Gateway → Interview → AI Gateway 的 context 链可能在 LLM 调用完成前被取消
- 流水线通过 `context.Background()` 绕过

### 2. AI 配置加载失败
- `ai_configs` 表可能缺少 `interview_agent`、`plan_agent`、`companion_agent` 等场景的配置
- 流水线使用 `question_generator` 场景，可能已在 admin 后台配置
- 但 `admin_configs` 兜底机制应该能覆盖（`ai_config_repo.go:52`）

### 3. Prompt 模板缺失
- `prompt_seed.go` 种子数据场景名为 `interview`、`companion`、`quiz`、`plan`
- 代码中场景名为 `interview_agent`、`companion_agent`、`quiz_analyzer`、`plan_agent`
- 但 `prompt_repo.go:39` 的 `promptSceneCandidates` 已做兼容映射
- **可能性较低**，除非种子数据未插入且无手动配置

### 4. ARK LLM API 调用失败
- API Key、Model Endpoint 配置错误
- 但流水线也调用同一 LLM，应同样受影响
- **除非**不同场景使用不同的 model/api_key 配置

## 建议排查步骤

1. **查看 AI Gateway 运行日志**：确认具体错误是 `LLM_CALL_FAILED`、`AI_CONFIG_NOT_FOUND` 还是 `PROMPT_RENDER_FAILED`
2. **检查数据库 `ai_configs` 表**：确认各场景是否有 active 配置
3. **检查数据库 `admin_configs` 表**：确认 `ai_api_key`、`ai_model`、`ai_base_url` 等全局配置是否正确
4. **检查数据库 `prompt_templates` 表**：确认各场景模板是否存在且 active

## 推荐修复方向

如果确认是 context 超时传播问题，参考流水线的做法，为所有 AI 场景的 LLM 调用创建独立 context：

**修改文件**: `app/ai_gateway/internal/biz/ai.go`

将所有 `uc.llm.Chat(ctx, messages, cfg)` 改为使用独立 context：
```go
llmCtx, cancel := context.WithTimeout(context.Background(), 3*time.Minute)
defer cancel()
resp, err := uc.llm.Chat(llmCtx, messages, cfg)
```

涉及的 UseCase 方法：
- `InterviewAgentUseCase.GenerateQuestion()` (line 153)
- `PlanAgentUseCase.GeneratePlan()` (line 241)
- `CompanionAgentUseCase.Chat()` (line 317)
- `QuizAnalyzerUseCase.Analyze()` (line 418)
- `ResumeParserUseCase.Parse()` (line 494)
- `Live2DDirectorUseCase.GenerateDirective()` (line 592)

以及 `structured_output.go:81` 中 `parseStructuredJSON` 的 JSON 修复调用。
